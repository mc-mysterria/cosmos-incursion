# Cosmos audit event catalog

All events are prefixed `mysterria-cosmos.` and use `STAFF_RESTRICTED` privacy. Rows go through the shaded audit client to the bounded spool under `plugins/mysterria-audit-spool`; the optional audit engine ingests them into SQLite for staff search. Emission is best-effort and never affects gameplay. Incursion rows use the incursion UUID as correlation ID, except a queued MVP reward paid on join, which sums every queued incursion and gets its own correlation ID, and `incursion.acting_granted` rows, which use their own operation UUID; each shop purchase has one correlation UUID and business ID `zone-shop.purchase.<uuid>`. Rows involving a player carry `world`/`x`/`y`/`z`; resource amounts are keyed `gold`/`silver`/`gems`.

Staff rows (`admin.*`, plus the forced `incursion.created` and `admin_force_stop` rows) use their own operation UUID as correlation ID, and the staff member is the actor: a player's UUID is the actor ID, while console and RCON have no UUID and are identified by `actor_name` (for example `CONSOLE`) and `actor_type` `console`. Each row is written by the command handler from state already in hand, on the thread the command runs on, with no scheduler hop. Exclusion-zone rows are COMMITTED only when the zone file write succeeded; a failed write is FAILED with `applied_in_memory` true, because the change stays live until restart. `/cosmos admin balance` and the shop editor keep their existing rows (`town.balance_adjusted`, `admin.zone_shop_edited`).

`incursion.zone_death` notes. The row is built from the death event, the victim and the zone state already in hand and is emitted on the death event before any gameplay early return, so it adds no scheduler hop, lookup or IO. It uses the incursion UUID as correlation ID, or its own operation UUID when no incursion is active. `counted_for_rewards` means the kill passed the same gate as PvP acting and crate rewards (a distinct player killer who is not a Corrupted Monster and not a griefing kill); the amounts actually granted are in the `incursion.acting_granted` rows. Incursion scoring for winners and MVPs has no per-death input. The kill and death counters on the `incursion.completed` row count every death in an incursion zone and every death with a distinct player killer, whatever the reward gate decided. A player owner is only reported when Bukkit already exposes it on the damage source or on a tamed entity (UUID only). Owners of CircleOfImagination summons, projections and Wild Beyonders are not reported, because no API in use exposes them without a new lookup. A death is recorded only when the victim has a player zone state; a player who dies inside the zone radius before that state exists is not seen by the zone-death path at all.

Death consequence rows (`exclusion.*`, `incursion.items_dropped`, `death_penalty_applied`, `death_penalty_skipped`, `characteristic_dropped`, `paper_angel_*`, `kill_reward_command`, `cosmos_crate_granted`, `hollow_body_*`). These automatic rows are written at the event, next to the code that already makes the change and after it has run: COMMITTED or FAILED where the code has a result (a dispatch result, a created beyonder, a spawned entity), OBSERVED where it has none (item drops). Each is built from objects the code already holds and emitted directly on the calling thread, with no scheduler hop, IO or lookup made only for the row; a failure is counted and never thrown. They use the incursion UUID as correlation ID, or their own operation UUID when no incursion is active, and have no actor unless stated above. Nothing about a death is changed by a row: the penalty, drop, reward and resource code paths run in the same order as before, and a thrown exception is rethrown after its FAILED row.
- Item drops list `material` and `amount` per stack, taken from the stacks the drop loop already holds. CoI `item_uuid` is left out: the drop code never reads it, and reading each stack's metadata would be a lookup made only for the row. A GREEN death with no player killer is not processed by the game, so it has no item row; its `incursion.zone_death` row says so. The drop row is written once per processed death, including a death that dropped nothing.
- `incursion.death_penalty_applied` takes its values from locals inside the existing penalty method. `acting_after_calculated` is acting before minus the penalty and is not read back from CoI; after a regression the total acting of the new beyonder is not read back either, only the amount added (`acting_restored`). `beyonder_recreate_failed` means the old beyonder was destroyed and could not be created again at the next sequence. A DEATH-tier death that skips the penalty because the victim is not a beyonder, the sequence is above the regression threshold, or the penalty cooldown is running writes `incursion.death_penalty_skipped` with that reason (one row per death, written beside the existing log line from the values it prints); a Paper Angel that blocks the penalty writes `incursion.paper_angel_consumed`. A death outside the DEATH tier has no penalty by design (item drops are the only punishment), so it writes no skip row; its tier is on the `zone_death` row. A beyonder with no resolvable pathway writes `death_penalty_applied` with `no_penalty_applied`. The cooldown start is not recorded when a Paper Angel blocks the penalty (existing behaviour).
- `incursion.kill_reward_command` is written for every distinct player kill in a tier that has a reward command, including kills that fail the crate gate, because the command runs before that gate. `dispatched` false means Bukkit did not run the command. The crate row from the death handler is DENIED with `griefing_or_corrupted_killer` and cannot say which of the two applied without a lookup.
- A Paper Angel click refused because the player is already protected writes `incursion.paper_angel_refused`. The click can be repeated every tick, so one row is written per player and reason per 60 seconds and the next row counts the swallowed refusals in `suppressed_since_last_row`; the window state is two fields per online player and is dropped on quit, so a relog starts a new window. `already_protected` is the only refusal the handler has: a click on any other item is ignored before the handler acts.
- `exclusion.resources_lost` reads the amounts from the buffer the removal returns, so it adds no lookup; it is skipped when the buffer was empty. `exclusion.resources_transferred` carries no zone fields and no resulting killer total, because the listener holds neither. `exclusion.resources_spilled` covers resources that spill onto the ground in spectator mode and when a player quits, from a copy of the buffer taken before the spill clears it; both spills drop one reclaimable item per type with the exact carried amount, so nothing is lost to rounding or a stack cap. The spectator row is written at the spill, even if a later handler cancels the mode change (the existing code spills regardless); who forced the mode change is not on the event, so there is no actor, only `game_mode_cause`. A cancelled extraction channel is not reported, because that needs a channel lookup made only for the row. Picking a spilled item back up is not covered.
- A combat-log body death is written when Citizens reports the NPC death, from the Citizens death event, so the killer fields are the ones the event carries. A body whose NPC times out (`despawn_reason` `timeout`) or is removed at event end (`event_end`) writes `incursion.hollow_body_despawned`, and a body whose reconnect state is forgotten after the grace period writes `incursion.hollow_body_evicted`; both are written from the hollow body the cleanup already holds, once per body. The code keeps no position after spawn, so both rows carry the spawn location; the despawn row reports the items still held (`held_*`) only as counts, because the stacks are listed on the eviction or kill row when they are dropped. Citizens destroy errors are swallowed by the existing removal code, so the despawn row records the state change and not a confirmed destroy. The inventory restore for a surviving body when its owner reconnects, and a body removed on reconnect, write no row.
- Not covered: deaths cancelled at LOWEST by another plugin, victims with no tracked zone state (incursion or permanent), and CircleOfImagination summon owners, for the reasons given above.

## Main thread

Rows add no main-thread reads made only for the row. Zone shop rows describe items by material and amount from the stacks the purchase code already holds: item meta and CoI tags are not read, so `shop.*` and `admin.zone_shop_edited` rows carry no `item_uuid` or `parent_item_uuid`. Rows written before the item is resolved (pre-confirmation DENIED, `insufficient_balance`, `item_resolution_failed`) carry the shop and CoI item IDs only, with no `item` field. A dropped overflow stack is recorded from the stack the shop dropped, with the player's location. `admin.command_observed` does not check the sender's permission.
